# NestJS Four-Layer DDD + CQRS Learning Curriculum

Every playthrough follows this 8-phase curriculum. The point is to repeat the same architecture with different **domain + tier** choices until the pattern becomes natural.

## Three Tiers

The key choice in the workflow is **domain + tier**. The tier is the difficulty of the learning scope, not the domain itself.

| Tier | Scope | Key Learning Points |
|---|---|---|
| **Basic** | 1 Aggregate Root, simple state transition, single BC | VO pattern, Aggregate Root, single CQRS |
| **Intermediate** | 2 Aggregate Roots, 1-2 BCs, cross-aggregate validation | Multi-Aggregate, Cross-BC Port, Domain Service, composite VO such as DateRange |
| **Advanced** | 3+ Aggregates, 2+ BCs, Domain Events, Saga | Eventual Consistency, Process Manager, ACL, policy engine |

Examples:
- `inventory-management` + `basic` -> one Product Aggregate with simple stock changes.
- `inventory-management` + `intermediate` -> Product plus StockMovement history.
- `inventory-management` + `advanced` -> stock-reservation Saga and multiple warehouses.

Selection guidance:
- Start with **basic** if this is the first attempt.
- After completing `order-management`, try **intermediate** to learn Cross-BC Port and Domain Service patterns.
- Attempt **advanced** after becoming comfortable with Saga and Domain Events.

## Phase -1: Domain Design (Strategic + Tactical)

**Goal**: clarify the domain model before coding.

**Outputs**:
- Strategic: `workspace/<playthrough>/docs/strategic-design/`, generated by `/strategic-design --prd ...`.
- Tactical: `workspace/<playthrough>/docs/DESIGN.md`, written interactively.
- Progress: `workspace/<playthrough>/docs/PROGRESS.md`.

Strategic Design is handled by the skill. Tactical Design receives the BCs and Ubiquitous Language from STRATEGIC.md and defines the implementation-level model.

### Required Sections

```markdown
# <Sub-Project Name> Domain Design

## Domain Overview
- One-line summary
- Two or three core scenarios: what users do

## Aggregate / Entity
- **Aggregate Root**: name and responsibility
- **Entity**: name, responsibility, and owning Aggregate

## Value Objects
| VO | Values | Validation Rules |
|---|---|---|
| XxxId | string (UUID) | - |
| Money | amount, currency | non-negative amount, matching currency |

## State Transitions
PENDING -> CONFIRMED -> SHIPPED -> DELIVERED
              |
              v
           CANCELLED

## Use Cases
| Action | Type | Input | Output |
|---|---|---|---|
| Create | Command | customerId, items | void |
| Get | Query | id | Order |
| Confirm | Command | id | void |

## Expected API Endpoints
| Method | Path | Action |
|---|---|---|
| POST | /orders | Create |
| GET | /orders/:id | Get one |

## Business Rules
- Can confirm only from PENDING.
- Cannot cancel after SHIPPED.
- Add domain-specific rules.

## Domain Exceptions
- InvalidXxxStateException
- XxxNotFoundException
```

### Verification

- Can a first-time reader understand the domain from DESIGN.md?
- Are Aggregate boundaries clear?
- Are state transitions shown as a diagram or table?

## Phase 1: Domain Layer

**Goal**: pure business rules with no framework dependency.
**Learning points**: Value Object immutability, Aggregate Root, domain invariants.

### 1.1 Value Objects

- ID VO per Entity, such as `OrderId` and `OrderItemId`.
- Value VO such as money, quantity, and status enum.
- Pattern: `private constructor` + `static create()` + `equals()` + immutable `readonly` values.

### 1.2 Domain Models

- Entity such as `OrderItem` has its own ID.
- Aggregate Root such as `Order` owns state-transition methods and encapsulates rules.
- Separate `reconstitute()` factory for restoring from persistence.

### 1.3 Factory

- Builds Aggregates from raw input.
- `@Injectable()` is allowed in this project.

### 1.4 Repository Port

- Do not create a separate domain repository interface here.
- Define repository Ports in Phase 2 under `application/ports`.

### Verification

```bash
npx tsc --noEmit
rg "from 'typeorm'" src/<domain>/domain/
# Expected: no results
```

## Phase 2: Application Layer

**Goal**: split commands and queries with CQRS and define Ports.
**Learning points**: abstract class as DI token, handlers delegate to domain models.

### 2.1 Port

- `application/ports/<aggregate>.repository.port.ts` as an `abstract class`.
- Reason: TypeScript interfaces disappear at runtime and cannot be DI tokens.

### 2.2 Commands

- Data containers with no logic.
- Create one Command for each domain state change.

### 2.3 Command Handlers

- Use `@CommandHandler(XxxCommand)`.
- Pattern: findById -> call domain method -> save.

### 2.4 Queries + Handlers

- Use `@QueryHandler(XxxQuery)`.
- Specify return type through `IQueryHandler<Query, Result>`.

### 2.5 Thin Service Facade

- Inject `CommandBus` and `QueryBus`.
- Keep controllers unaware of handlers.

### Verification

```bash
rg "from '.*infra" src/<domain>/application/
# Expected: no results
```

## Phase 3: Infrastructure Layer

**Goal**: implement Ports with TypeORM and map between domain and ORM.
**Learning points**: ORM entity is not domain model, Mapper pattern.

### 3.1 ORM Entities

- Use `@Entity`, `@Column`, `@OneToMany`, and `@ManyToOne`.
- Do not forget relationship delete policies such as `onDelete: 'CASCADE'`.

### 3.2 Mapper

- `toDomain(orm) -> Domain`: use `reconstitute()` when reading from DB.
- `toOrm(domain) -> ORM`: create an ORM entity and assign properties.
- Mapper needs `@Injectable()`.

### 3.3 Repository

- Extend `XxxRepositoryPort`.
- Inject TypeORM repository with `@InjectRepository(...)` and inject Mapper.
- Load related ORM entities explicitly through `relations` options.

---

## Phase 4: Presenters Layer

**Goal**: map HTTP requests to Command/Query and domain models to response DTOs.
**Learning points**: DTO validation and response mapping.

### 4.1 Request DTOs

- Place under `presenters/http/requests/`.
- Use `@IsString`, `@IsNumber`, `@ValidateNested`, `@Type`, and similar validators.

### 4.2 Response DTOs

- Place under `presenters/http/responses/`.
- Use `static fromDomain(model)`.
- Instantiate with `new` to make the response shape explicit.

### 4.3 Controller

- Use `@Controller('<resource>')` and endpoint decorators.
- Inject Service and return Response DTOs.

---

## Phase 5: Module Wiring

**Goal**: connect all layers through NestJS DI.
**Learning points**: Port-to-implementation binding happens in one module only.

### 5.1 Domain Module

- Import `CqrsModule` and `TypeOrmModule.forFeature([...])`.
- Register Controllers and Providers: Service, Factory, Mapper, and Handlers.
- Key binding: `{ provide: XxxRepositoryPort, useClass: XxxRepository }`.

### 5.2 AppModule

- Configure DB through `TypeOrmModule.forRoot(...)`.
- Import the domain module.

### 5.3 main.ts

- Register global `ValidationPipe` with `whitelist`, `forbidNonWhitelisted`, and `transform`.
- Register `DomainExceptionFilter` in Phase 7.

### Verification

```bash
npm run start:dev
# Expected: CREATE TABLE logs and Nest application successfully started
```

## Phase 7: Domain Exception Handling

### 7.1 Domain Exception Classes

- `domain/exceptions/domain.exception.ts` as the base `abstract class extends Error`.
- Concrete exceptions such as `InvalidXxxStateException` and `XxxNotFoundException`.

### 7.2 Replace Generic Errors

- State-transition violation -> `Invalid...StateException`.
- Lookup failure -> `...NotFoundException`.

### 7.3 NestJS Exception Filter

- `presenters/http/filters/domain-exception.filter.ts`.
- `@Catch(DomainException)` maps domain exceptions to HTTP statuses.
- Register globally in `main.ts` with `app.useGlobalFilters(...)`.

## Phase 8: Unit Test Strategy

| Layer | Test Type | Mock |
|---|---|---|
| Domain (VO, Model) | Pure unit test | None |
| Application Handler | Unit test | Port only |
| Infra (Repository, Mapper) | Integration test | Real SQLite |
| Presenters (Controller) | e2e test | Service only |

Core principle: if a Domain test needs mocks, the domain design is probably wrong.

Synchronize Jest `moduleNameMapper` with path aliases.

## Shared Architecture Rules

| Rule | Reason |
|---|---|
| No framework imports in `domain/`, except the local `@Injectable` exception | Easy isolated tests and framework replacement |
| No `infra/` imports in `application/` | Dependency inversion |
| Port is an `abstract class` | Usable as runtime DI token |
| Mapper exists only in `infra/` | Single responsibility for ORM/domain conversion |
| Module is the only wiring point | Swap implementation by changing one module |
| Separate ID VO for each Entity, such as `OrderId` versus `OrderItemId` | Type safety and fewer mistakes |
| Separate `create()` and `reconstitute()` | Clear distinction between new object creation and DB restoration |
